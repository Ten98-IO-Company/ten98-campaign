# Zernio advertising coverage and remaining work

Updated 20 October 2026 for the current bounded increments; the wider inventory originated with the **v0.8.9 expansion**. Touched contracts use cached official OpenAPI **1.295.0**. This records implemented subsets and remaining work, without claiming live advertising acceptance or spend. Current evidence and run logs are maintained in the [accepted checkpoint](verification.md#current-accepted-checkpoint).

The app has a basic creation route for all eight advertising networks Zernio currently lists. It does **not** implement every feature of those networks. The largest remaining areas are advanced creative formats, audiences, measurement, leads, product catalogs, detailed reporting and account operations. The shared HTTP client does not make an endpoint available to users: explicit server validation, project scoping, permissions, UI and recovery are still required.

The unreleased increment adds scoped Meta interest search and exact-ID/name selection for new ads. The isolated browser accepted selection and scope clearing at 320px without an ad write; later targeted checks cover discarded callbacks. Current candidate and acceptance gates are recorded in [canonical verification](verification.md#current-accepted-checkpoint). The C1–C8 library integration remains accepted. Native provider budgets, targeting and version-bound lead-form review remain in `AdComposer`; `RunCostSummary` does not represent advertising budgets. This closes one targeting subset. Shared terminal unsent recovery also covers conversion and lead-confirmation actions: a blocked new key retains its own failed receipt, drafts survive and a new action requires explicit fresh review; outcome checks cannot become first dispatches after prior review. The main key map also releases an own failed receipt independently of HTTP status; a preflight 502 cannot retain a failed key as unknown, while truly own pending/uncertain outcomes remain blocked. Historical 931/0.3.14 and earlier receipts remain in [rolling verification](verification.md#rolling-follow-up-verification). The earlier 905 checkpoint includes collection filtering/title renaming and inbox search reconciliation; 913 adds validated Instagram login-method/reconnect previews, stale authorization-link invalidation and native-snapshot failed-copy retry guards. These add no further advertising parity or live acceptance. The qualified 924/0.3.11 candidate remains historical. The historical 931 checkpoint includes status-only ad-set controls, read-only Meta/Google/TikTok review and the bounded A06 paused-copy slice. The independent 0.3.12 ad-set/error probe and actual current Overview/Inbox samples pass within their recorded bounds. That historical checkpoint's container/smoke and bounded Meta live-review/copy browser gates passed; its 0.3.14 full-library gate passed 166/166 in 3.4 minutes. The historical stable [0.3.14 release](https://github.com/Ten98-IO-Company/ten98-design-system/releases/tag/v0.3.14) was independently confirmed through release metadata as non-draft and non-prerelease, targeting commit `e4777c877cbd99075fa2945f158ec6d4d96617d4`; the installed artifact SHA-256 is unchanged. The 931-test full application run predates the final native Broadsign color-pair correction. After that single-pair change, four focused checks, production build, container build and non-root/read-only/network-disabled smoke passed; the actual bounded dark Broadsign after capture and final Inbox top capture are accepted. Light Broadsign contrast remains a source assertion, without actual light browser acceptance. [Historical paint receipts](verification.md#rolling-follow-up-verification). LinkedIn/other-platform browser acceptance is not claimed. The accepted 829-check C1–C8 milestone on 0.3.9 remains historical and separate. Those historical route pins remain in the [final source record](../.cache/theme-audit/final-after-pins.json); later acceptance and remaining gates are recorded in the [current checkpoint](verification.md#current-accepted-checkpoint).

Discovery used [Zernio's documentation index](https://docs.zernio.com/llms.txt), its linked resource pages, and the official OpenAPI snapshot labelled `1.292.0`. The advertising census contains **251 HTTP operations across 156 paths** when including `/v1/ads`, account tracking tags, conversion destinations/custom conversions and the related advertising connection paths. These are operation counts, not distinct user features or a coverage percentage.

The advertising resource tags alone contain 247 operations across 152 paths; four advertising connection operations bring the scoped total to 251. Two scoped operations are deprecated. The entire API snapshot contains 966 operations across 631 paths, including 23 deprecated operations.

**Reddit compatibility fix implemented in v0.8.5:** every create/boost goal now requires an explicit pixel. The builder supports all five documented goals, website leads, daily/lifetime budgets with required lifetime end dates, and promotion of a verified published Reddit copy from this project. Pixel discovery and synthetic-provider browser creation/boost are verified; full Reddit targeting, lifecycle and conversion ingestion remain incomplete.

## Status and evidence

- **Implemented**: a specific documented operation has an explicit application handler and usable UI for the bounded scope described.
- **Partial**: the family exists, but supported fields, operations or UI are incomplete.
- **Missing**: no usable app workflow was found for the documented family.
- **Unavailable**: Zernio or the underlying provider explicitly does not expose it, or access requires a provider beta/eligibility grant.

These labels describe code coverage. Existing mocked HTTP, browser and regression checks are recorded in [audit coverage](audit-coverage.md); they do not establish live account eligibility, review approval, delivery or spend.

## Shared completion rules

1. **Use the existing handlers and receipt system.** Extend the explicit contract where it belongs; do not introduce an unrestricted provider proxy or a generic JSON editor as a substitute for feature support.
2. **Enforce permissions twice.** UI availability follows workspace role; the server rechecks project/profile/account ownership, active session and credential/mapping revisions at the write. Connection/admin operations remain separate from editorial campaign changes.
3. **Read before editing.** Load current provider configuration, distinguish synced/live/stale state, preserve fields not edited and summarize the affected campaigns, groups, placements or products.
4. **Recover writes without duplicate spend/resources.** Keep the same intent/key after an unreadable or lost receipt, retain partial success and require reconciliation where the provider has no idempotency/readback guarantee. A new button click must not silently mint a new upstream operation.
5. **Leave one meaningful regression check per nontrivial change.** Use actual application handlers and isolated provider fixtures. Cover successful receipt, permission/scope failure, malformed receipt, timeout/unknown result and reload/retry; add browser acceptance for the user-facing create/edit/recovery flow.
6. **Separate local acceptance from live acceptance.** Fixtures can confirm app behavior and outbound shape. Real provider acceptance additionally needs configured credentials, account eligibility, granted scopes, approved assets and review; these must be verified separately before claiming live delivery works.
