# Zernio messaging and engagement coverage

Updated 19 October 2026 for the **v0.8.9 expansion**, against the official documentation and OpenAPI **1.292.0**. This records implemented subsets and remaining work; missing features have not been built, and live provider acceptance is not established. Repository evidence is the current checkout; automated and synthetic-provider browser evidence is described in [verification](verification.md).

Understood as: bring every relevant, available Zernio messaging and engagement capability into the campaign manager, including its settings, user workflow, permission checks, recovery and verification. Preserve the user's exclusions: no voice calling; Cloudflare email remains transactional; incoming email continues through external routing to the receiving mailbox or group.

The [documentation index](https://docs.zernio.com/llms.txt) was used for discovery. Individual primary documentation pages below establish the feature claims. Platform publishing fields are also covered by the separate social-publishing inventory. Sender provisioning, RCS registration, phone-number administration and provider administration belong in the consolidated inventory, rather than being counted again here.

## How to read the status

| Status | Meaning |
| --- | --- |
| Implemented | The named action has a reachable app workflow and a server handler. This does not imply that every option in its wider API family is supported. |
| Partial | A usable subset exists; the precise omitted behavior is named. |
| Missing | Zernio documents the capability, but the app has no complete corresponding workflow. |
| Unavailable | The provider documentation explicitly withholds the feature or limits its availability. This is separate from an app implementation gap. |

### Meta Business Agent: 55 operations

This expands the single Missing family above; the counts are API method/path operations, not 55 additional completed workflows. Every route uses the base `/v1/accounts/{accountId}/business-agent`. **Zernio exposes this suite, so a native Meta integration is not required.** The current `server` and `src` code contain no Business Agent adapter or management screen. [Provider overview](https://docs.zernio.com/platforms/whatsapp/business-agent).

The number must be eligible and Cloud API managed. The merchant must manually accept Meta's terms in WhatsApp Manager and attach the agent's payment method in Billing Hub. Status distinguishes verifiable `manualSteps` from `unverifiedSteps`: Meta exposes no payment-readiness state. An enabled agent or successful sandbox test must not be labelled as verified production billing. [Setup status and manual gates](https://docs.zernio.com/business-agent/get-business-agent-status).

## Platform limits that must stay visible

These are not missing app features to promise away:

- **Discord:** inbound DM replies, comments and native message analytics are unavailable through Zernio. Outbound DMs do not create a two-way Discord inbox. [Discord limitations](https://docs.zernio.com/platforms/discord).
- **Telegram:** no comments feed or native post analytics; bot administration and supported messages are still implementable. [Telegram limits](https://docs.zernio.com/platforms/telegram).
- **Slack:** the inbox receives DMs, mentions and relevant threads rather than every channel message; native post analytics are unavailable. [Slack inbox boundaries](https://docs.zernio.com/platforms/slack).
- **WhatsApp:** group administration requires a Cloud API-only number; free-form session messages are time-limited; flows are distinct from Zernio automation workflows. [WhatsApp overview](https://docs.zernio.com/platforms/whatsapp).
- **Instagram reactions:** the documented limited-release access cannot be made generally available by adding a button. [Instagram release gate](https://docs.zernio.com/comments/like-inbox-comment).
- **User scope:** voice calls and call workflow nodes remain excluded. Incoming email stays outside this inbox. These are intentional product decisions, not Zernio limitations.

Every new write must recheck project membership, account/profile mapping and current eligibility immediately before dispatch; use the existing durable operation receipt and retain the same action key/draft after an unreadable or uncertain acknowledgement. A read after a successful write may fail without turning the confirmed write into a failure.
